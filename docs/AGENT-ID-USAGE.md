# Agent ID usage description (for the hackathon submission form)

**Project:** AgentPay ID
**Chain:** BNB Chain (BNB Smart Chain, chainId 56)
**Agent ID registry:** SPACE ID Agent ID, `0x60b9262456de011f7d15a54cdd8c48baaa8b022f` (ERC-721, non-transferable)

## How Agent ID is used — in the product's core flow, not as decoration

AgentPay ID calls `balanceOf(address)` on the Agent ID registry — the exact
check documented in the hackathon announcement — in three places:

1. **Sender gate (access control).** `checkIn()`, `payBNB()` and `payToken()`
   all carry an `onlyAgent` check: the transaction reverts unless the caller
   holds an Agent ID at execution time.
2. **Recipient gate (payment safety).** Both payment functions revert unless
   the *recipient* also holds an Agent ID. Identity verification is therefore
   enforced by the contract itself at the moment value moves, not just by the
   UI. The frontend additionally checks before enabling the Pay button and
   re-checks immediately before sending.
3. **Reputation identity.** Check-in streaks and points accumulate against the
   Agent ID holder's address and are exposed via `profileOf(address)` so other
   dApps can consume "is this a real, active Agent ID identity?" as a signal.

## Interaction metric

The contract counts distinct Agent ID holder addresses that have signed an
interaction in `uniqueInteractors` (first check-in or payment), and exposes
`totalCheckIns` / `totalPayments` — the same on-chain data the Growth Award
ranking is based on. Innovation Award eligibility (≥30 interacting Agent ID
addresses) can be read directly from `uniqueInteractors`.

## Explicit non-uses

- Agent ID is **not** used to look up other people's wallets by name: there is
  no name resolution anywhere. A payment link is generated by a holder for
  their *own* address and shared by choice.
- Possession is re-checked on every call; nothing is cached off-chain.
